# 5.16.4 日志与周期通信的响应性修复

此前版本在界面线程写入 `taskbar-events.log`，在 Explorer 任务栏线程写入 `adapter-events.log`。文件很小也不能保证写入立即返回：打开、查询属性、轮转或追加任何一步等待存储，都可能延迟界面消息和任务栏操作。普通测试原先跳过日志写入，因而没有覆盖这种退化情形。

另一条问题路径是周期更新超过 1500 毫秒等待上限后，在同一次界面消息中立即发送停止命令，再花一次等待预算。用独立跨线程窗口阻塞真实 `WM_COPYDATA` 端点，连续两次测到一次刷新花费 3010 和 3015 毫秒。

## 改动

- 宿主和适配器共用有容量上限的日志写入器。生产调用只尝试入队，队列满时丢弃诊断记录；文件操作与 `OutputDebugStringW` 在后台执行。每个写入器最多排队 128 条，每条最多 4096 字节。
- 异常诊断回调使用 16 个固定缓冲区与原生事件通知，回调不再打开或写入文件。槽位只发布一次，计数饱和后停止记录；多线程预留不会复用已发布的数据。适配器线程和回调发布前先保持 DLL 生命周期。
- 修复 Windows 上旧轮转文件已存在时，重命名失败却继续追加的问题。当前文件超过预算前先轮转，轮转失败不继续增长；正常单写入器下保留当前和上一份各 256 KB。
- 周期更新、自动停止步骤以及周期恢复查询的通信上限为 250 毫秒。更新失败后先返回界面；停止命令确认收到后，再由下一次消息查询恢复状态。
- 收到停止命令的确认仍不等于完成恢复。只有原会话报告 `Closed` 或原进程退出才释放连接。三次失败预算、恢复阻塞状态以及后续只读确认仍然保留。
- 宿主消息循环结束后最多等 100 毫秒排空日志，避免正常退出轻易丢掉最后的恢复记录；存储仍阻塞时按时退出，不等待写入线程结束。

启动握手与用户主动停止仍保留原有的较长确认等待。周期等待上限缩短后，繁忙的任务栏会更早进入恢复流程；此变化已通过连接保留和恢复确认回归检查。操作系统调度、重入回调及其他保存操作并不受这个通信参数的硬性约束。

## 验证

以下回归走真实调用入口，使用独立窗口/线程和受控日志写入器，不接入桌面的 Explorer：

- `taskbar_service::tests::native_timer_recovery_keeps_messages_responsive_when_log_io_stalls`：阻塞日志消费者，确认真实 `WM_TIMER → Service::tick → session fault` 之后的界面消息仍能处理。修复前连续两次失败，修复后通过。
- `platform::taskbar_clock::restoration_checks::stalled_endpoint_cannot_combine_tick_and_stop_waits_in_one_ui_dispatch`：真实跨线程 `SendMessageTimeoutW`。修复前约 3.01 秒；修复后约 255 毫秒，并检查停止与恢复确认分开执行、停止确认不重复发送命令。
- 日志队列饱和、退出排空超时、重复轮转失败、适配器调用不等写入、模块保持顺序与异常槽位并发唯一性均有回归检查。

在发布版基准提交 `addaef6` 的独立检出中，增加仅用于本次测量的计数器和私有 XAML 窗口。每个场景预热 10 次、记录 80 次，调用生产 `Session::receive/poll`、绑定及拓扑检查、托盘刷新和日历/音量输入的暂停/启用。

| 私有场景 | 一轮更新与检查的 P95 | 不变模型的重复改写 |
| --- | ---: | ---: |
| 1 个时钟，无托盘镜像 | 约 0.84 ms | 0 |
| 3 个时钟，20 个模型，两个文本控件 | 约 2.96 ms | 0 |
| 3 个时钟，20 个模型，共用文本控件 | 约 2.79 ms | 0 |
| 3 个时钟，128 个模型，共用文本控件 | 约 2.70 ms | 0 |
| 8 个时钟，512 个模型，共用文本控件 | 约 6.55 ms | 0 |

所有场景均保持会话有效并确认停止恢复。测量没有复现持续高开销或不变托盘模型被反复重设。私有控件不能等同 Explorer 的私有图标模型、系统菜单或显卡竞争，因此这些结果只限定相关生产模块的健康路径开销，不代表整机性能验收。

## 本次调查的边界

这两项软件问题已经复现并修复，但不能仅凭隔离测试反推某次整机卡顿的最初触发者。事后日志缺少发生瞬间的线程栈、进程 I/O 跟踪及图形呈现跟踪。

旧适配器的异常回调采用永久保持模块的机制。宿主退出后，旧 DLL 可能仍映射在 Explorer 中；映射本身不代表时钟或托盘计时器仍活动。旧回调也不会因修改源码而自动替换，后续实际验证需要一个新建的 Explorer 进程环境。本轮没有重启 Explorer，也没有安装或启动新版本。
